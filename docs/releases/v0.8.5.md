# Industrial Maintenance Agent v0.8.5

Public real industrial device data adapter.

## Why this release

Every device answer this service gave until now came from `data/devices.json`:
five records with round numbers, written to make the pipeline demonstrable and
testable. `PLC-001` reporting 78.0 degrees is not a measurement from any machine.
That is fine for a demo and inadequate as evidence that the service can handle
data a real asset produced, where readings are noisy, timestamps come from
upstream, some channels disagree with each other, and no field means quite what
the demo record's fields mean.

This release adds a second device source backed by a public real-world dataset,
without moving the frozen benchmark, the tool contract or the default behaviour.

## Added

- `app/integrations/device_data/`, an abstraction for externally sourced device
  readings: `DeviceDataAdapter`, an immutable `DeviceSnapshot`, a distinct
  `DeviceDataSourceError`, and a configuration-driven factory. No adapter touches
  the filesystem at import time, so the service starts with or without a dataset.
- `MetroPT3Adapter`, a reader for the UCI MetroPT-3 dataset (dataset id 791, DOI
  `10.24432/C5VW3R`, CC BY 4.0): 1 Hz readings from a metro train air production
  unit, February to September 2020.
- The public device identifier `METRO-APU-001`, served by `get_device_status` and
  nothing else. The registered tool name and the input schema are unchanged, so
  the planner sees exactly what it saw before.
- Bounded reading. The CSV is about 208 MiB across 1.5 million rows, so a query
  reads the header and a bounded tail window, then caches the parsed record
  against the file's `(size, mtime_ns)` stamp.
- `METROPT3_CSV_PATH`, empty by default. With no path configured the source is
  not built at all, so it can neither answer nor fail.
- A `real-data` Compose profile, `agent-real-data`, which reuses the standalone
  image and bind-mounts a dataset directory read-only at `/external-data`. The
  host path comes from `${METROPT3_HOST_DIR:-./data/external/metropt3}`.
- `docs/data/metropt3.md`: publisher, DOI, licence, creators, the two
  accompanying publications, the field mapping, and the measured facts of the
  copy used for validation.
- `docs/evaluation/real_data_integration.md`: what this integration does and does
  not establish, including the full before/after drift measurement.
- `scripts/prepare_metropt3.py` to validate a local copy before relying on it. It
  never downloads anything and `--download-info` only prints the official
  location.
- `scripts/real_data_gate.py` and `scripts/real_data_agent_gate.py`, two gates
  with greppable verdict lines.
- `tests/test_device_data.py`, `tests/fixtures/metropt3_sample.csv` and
  `tests/fixtures/README.md`. The fixture is synthetic and the README says so, so
  it cannot be mistaken for a sample of the real dataset.

## Changed

The rule planner's identifier pattern was widened from
`([A-Za-z]{2,}-\d{3,})` to `([A-Za-z]{2,}(?:-[A-Za-z]{2,})?-\d{3,})`.

This was necessary, not incidental. Against `METRO-APU-001` the old pattern
cannot start at the first letter, skips ahead and matches `APU-001`, so the
device would have been looked up under a truncated identifier and reported as
unknown.

It is a lexer change and its impact was measured rather than asserted. The rule
planner was run over the frozen 49-case dataset immediately before and after the
change, in the same environment: **nine of nine metrics identical to full
precision**, no case changed outcome, and the dataset digest unchanged. The
dataset contains no two-segment identifier, so the new branch is never taken on a
benchmark case. Full table in `docs/evaluation/real_data_integration.md`.

Also changed:

- `DeviceStatusOutput` gained optional fields (`data_source`, `source_timestamp`,
  `measurements`, `digital_signals`, `status_derivation`, `error`). They are
  `None` for the seeded devices, whose behaviour is unchanged.
- `Dockerfile` copies `data/devices.json` and `data/alarms.json` by name instead
  of `COPY data ./data`. See the defect below.
- `.dockerignore` excludes `data/external`, so a 208 MiB dataset cannot enter the
  build context.
- `.gitignore` excludes every payload under `data/external/metropt3/`.
- `README.md` documents the second source, both Docker paths and the gates.

## Design decisions worth stating

**Status is derived, and says so.** The dataset publishes readings and no
ground-truth equipment state, so the adapter reports an operational state derived
from two documented control contacts, `DV_eletric` and `COMP`, cross-checked
against the published motor-current bands. The resulting labels are
`running_under_load`, `running_offloaded`, `stopped` and `observed`. Every
response carries `status_derivation`, and the answer renders it beside the status.
No fault, degradation or remaining-useful-life claim is made anywhere. There is no
model in this release and no prediction in it.

**Foreign readings are not reshaped.** `temperature`, `pressure`, `rpm` and
`alarm_code` exist because the demo rows have them. MetroPT-3 measurements are
not folded into those fields; they travel in `measurements` and `digital_signals`
under the dataset's own column names, with units in the keys. Fields the dataset
does not carry stay `null`.

**Three outcomes stay apart.** Device unknown (`found=false`, no error), source
configured but unreadable (`found=false`, with the diagnostic), and device found
all remain distinguishable, following the same contract the manual-retrieval tool
already used.

**Nothing is downloaded at run time.** The service reads the path it is given and
nothing else. Fetching the dataset stays a deliberate manual step.

## A defect this release caught

The first build produced a 1.37 GB image. The Dockerfile copied `data` as a
directory, so putting the dataset in `data/external/metropt3/` for validation
pulled 218 MB of CSV and archive into the build context, and the
`chown -R app:app /app` that follows duplicated it into a second layer.

Nothing in the build output named the dataset, and the container ran correctly
the whole time. Only the size was wrong, which is exactly the kind of failure that
survives a functional test suite. Fixed in both halves and pinned by tests. The
corrected image is 383 MB, matching the standalone shape before this release.

## Known limits

- The gates check one record, the last one. They are integration checks and not
  accuracy measurements, and they say nothing about how the derived status rule
  behaves across the full range of the dataset.
- There is no ground truth for equipment state, so the derived label cannot be
  checked for correctness, only for being declared derived.
- No benchmark case covers `METRO-APU-001`. Adding one would break the dataset
  hash lock that makes published reports comparable, so no metric changed and
  none should.
- The adapter serves one device and one record per query. It does not expose
  history, trends or windows.
- The dataset's own failure-report table is not used, and is not read.

## Upgrading

Nothing to do. The default configuration is unchanged: the external source is
absent, the seeded devices answer as before, and `get_device_status` keeps its
name and its single `device_id` parameter. To use the new source, download the
dataset from UCI as described in `docs/data/metropt3.md` and set
`METROPT3_CSV_PATH`, or start the `real-data` profile.
