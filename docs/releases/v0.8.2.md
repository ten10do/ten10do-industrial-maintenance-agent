# Industrial Maintenance Agent v0.8.2

First formal public release.

## Highlights

- Evidence-grounded industrial maintenance workflow
- Rule + LLM dual planner
- Structured tool calling
- Industrial RAG integration
- FastAPI service
- 49-case frozen evaluation dataset
- Three-run real DeepSeek planner stability benchmark
- GitHub CI
- MIT License
- Public repository hardening

The answer text is assembled from tool results and retrieved documents rather
than generated. The planner chooses which tools to call; the synthesis stage
renders what those tools actually returned.

## What ships in this release

- **Workflow** — a fixed five-stage graph: `route_query` → `plan_actions` →
  `execute_tools` → `retrieve_context` → `synthesize`.
- **Planners** — `PLANNER_MODE=rule` (default, deterministic, no LLM at any
  stage), `llm` (refuses to degrade on failure), and `auto` (prefers the LLM and
  falls back to the rule planner, recording why).
- **Tools** — three deterministic tools behind a shared registry:
  `get_device_status`, `query_alarm_code`, `search_maintenance_manual`. Each
  tool's JSON Schema is generated from its own input model; the executor
  re-validates against that same model.
- **Service** — `POST /agent/invoke`, `GET /`, `GET /health`, with correlated
  request ids, latency measurement and structured error handling.
- **Evaluation** — a framework kept separate from `tests/`, measuring agent
  capability against a hand-authored answer key.
- **Licensing and CI** — MIT license, and a hermetic GitHub Actions workflow.

## Benchmark summary

Measured on the frozen 49-case hand-authored dataset, planner-only, with no tool
execution. These figures describe this dataset and this configuration; they are
**not** a general model-accuracy claim.

Rule planner (single run):

| Metric | Value |
|---|---|
| Tool Exact Match | 79.59% |
| Tool Precision | 88.00% |
| Tool Recall | 98.51% |
| Task Success | 79.59% |

LLM planner (three-run mean, provider-reported usage):

| Metric | Value |
|---|---|
| Tool Exact Match | 80.27% |
| Tool Precision | 94.81% |
| Tool Recall | 90.55% |
| Task Success | 78.23% |
| OOD Tool Call Rate | 8.33% |
| Planning latency | ~1.41 s |

Notes on the numbers:

- The dataset is 49 hand-authored cases across seven categories, frozen before
  any planner was run against it. It is visible in `evaluation/dataset.json`,
  which is why planner changes belong in a later version scored on a holdout set
  this repository has never run.
- A ratio whose denominator is zero is reported as `null`, never as `1.0`. The
  `denominators` block in every report publishes the counts, so any ratio can be
  recomputed from the raw evidence in `evaluation/reports/`.
- Latency is wall-clock and varies across runs. Rule-planning latency is
  sub-millisecond; the LLM figure is dominated by the provider round trip.
- LLM figures are a three-run mean because a single run reported
  `planner_failure_rate` as exactly zero, which did not reproduce.

## Known Limitations

- LLM planner introduces significant latency
- LLM planner recall is lower than rule planner
- RAG coverage depends on external industrial corpus
- Docker image has not yet been runtime-validated if Docker daemon remains
  unavailable

Additional limitations carried forward from earlier releases:

- The `llm` planner mode has no fallback by design: a silently degraded plan is
  indistinguishable from a correct one, so it fails loudly instead.
- Planning is a single pass; there is no re-planning step.
- The planner prompt carries no conversation history and no prior tool results.
- `POST /agent/invoke` has no authentication and is intended for localhost.
- Manual retrieval re-reads its index and re-fits its TF-IDF model per call, so a
  manual query costs seconds rather than milliseconds. The reported `latency_ms`
  states the real cost rather than hiding it behind a timeout.
