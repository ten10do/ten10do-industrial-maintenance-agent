# Industrial Maintenance Agent v0.9.0

Production observability: structured logging, Prometheus metrics and optional
OpenTelemetry tracing, added without changing a single decision the agent makes.

## Why this release

Through V0.8.5 the service could be tested and benchmarked but not operated. It
logged one line per invocation, which answers "did it work" and very little else.
An operator running it could not answer how many requests were failing, whether
the retrieval path was slow or absent, how often the planner fell back, or what a
provider actually cost. The service was observable only in the sense that a log
file existed.

This release adds the three capabilities a production deployment expects, as a
layer that observes the pipeline from outside it. The constraint that shaped the
design is that observability must not be able to change an answer: the planner,
the tools, the graph and the integrations import no metrics or tracing library,
and the frozen benchmark was rerun before and after the change.

## Added

- `app/observability/`, the observability layer:
  - `logging.py`, structured events with an explicit redaction boundary and two
    output shapes produced from one call site;
  - `labels.py`, the frozen label vocabularies and the `bounded()` allow-lister;
  - `context.py`, a `ContextVar` carrying the request id through the pipeline;
  - `metrics.py`, `METRIC_SPECS` as the single declaration of the metric surface,
    on a private `CollectorRegistry` so a second import or a test cannot pollute
    the first;
  - `tracing.py`, OpenTelemetry spans with a deferred import, an attribute
    allow-list and no default exporter;
  - `instrumentation.py`, the only observability surface business code calls.
- `GET /metrics`, the Prometheus text exposition format. Eleven metrics covering
  the invocation, the planning step, the tool calls, the retrieval calls and the
  provider calls, plus provider-reported token usage.
- Structured event logging. `LOG_FORMAT=json` emits one object per line with a
  fixed field set; `LOG_FORMAT=text` remains the default and is byte-for-byte the
  format V0.8.5 emitted.
- Optional tracing. `OTEL_ENABLED=false` is the default and imports nothing at
  all. `requirements-otel.txt` holds the optional dependency set, and the
  `INSTALL_OTEL_DEPS` build argument adds it to an image.
- `docs/observability.md`: the architecture, the metric catalog, the label and
  cardinality policy, the span hierarchy, the configuration surface and the
  security policy.
- `docs/evaluation/observability_overhead.md`: the measured latency cost and the
  benchmark integrity check.
- `scripts/observability_overhead.py`: the harness those figures come from, with
  one process per configuration.
- `tests/test_observability.py`: 63 tests over metrics, labels, logging,
  redaction, tracing, the endpoint and the cardinality guards.
- `METRICS_ENABLED`, `OTEL_ENABLED`, `OTEL_SERVICE_NAME`,
  `OTEL_EXPORTER_OTLP_ENDPOINT` and `LOG_FORMAT` configuration.

## Design decisions worth stating

**The layer observes, it does not decide.** Planner, tool, graph and integration
modules call helpers in `app/observability/instrumentation.py` and import no
`prometheus_client` or `opentelemetry`. One consequence is that a metric name or
a label is a one-file change. Another is that a call site cannot invent a label,
because every value passes through `labels.bounded()`.

**Labels are allow-listed, not escaped.** Each label has one frozen vocabulary and
anything outside it becomes `other`. The largest metric has 120 series and no
request can raise that count. `request_id`, `device_id`, the query text, a
document path and an exception message are named in `FORBIDDEN_LABEL_NAMES` and
are asserted absent from every metric by the test suite. An exception message can
embed a provider URL and, on some transports, the credential-bearing headers, so
a planner failure records a closed reason such as `provider_error` and never the
message.

**Four outcomes, not two.** `success`, `not_found`, `unavailable` and `error` are
distinct. A device the deployment does not carry and a retrieval with nothing on
the subject are `not_found`, which is a correct answer to the question asked.
Reporting either as `error` would make a healthy service look broken and a real
outage indistinguishable from normal operation.

**Tracing off means doing nothing.** With `OTEL_ENABLED=false` neither the API nor
the SDK is imported, no exporter is constructed and no socket is opened.
`OTEL_EXPORTER_OTLP_ENDPOINT` has no default, because pointing one at
`localhost:4317` would turn an optional feature into a runtime dependency on a
process the operator may not have started.

**Metrics off still leaves the audit trail.** `METRICS_ENABLED=false` skips
recording and answers `404` on `/metrics`, and logging is unaffected. The log
contract predates this release and operators depend on it.

**`/metrics` answers 404 when disabled.** A collector treats a target answering
`200` as healthy. An operator who turned metrics off wants the target gone.

### Shape-specific evidence

**Standalone.** Seven invocations produced
`industrial_agent_requests_total{status="success"}` split across `device_status`,
`alarm_diagnosis` and `maintenance_advice`, with
`industrial_agent_tool_calls_total` showing `success` for `get_device_status` and
`query_alarm_code` and `not_found` for a device the catalog does not carry.
`search_maintenance_manual` reported `unavailable`, which is the correct outcome
for an image that deliberately omits the retrieval dependency set.

With `METRICS_ENABLED=false`, `/metrics` answered `404` and an invocation still
answered `200`. With `LOG_FORMAT=json`, every emitted line parsed as JSON (7
valid, 0 invalid) and the query text appeared in **zero** lines: the legacy
message renders `query='...'` for operators and the JSON formatter replaced it
with `query=<redacted>` before serializing.

**Tracing, in-container.** Against the `0.9.0-otel` image:

- `configure_tracing(enabled=True, otlp_endpoint="")` returned `True` and
  `is_enabled()` was `True`, so the SDK the image ships builds a tracer;
- `otlp_exporter_loaded` was `[]`, so the OTLP exporter is never imported when no
  endpoint is named;
- the whole pipeline ran with `socket.socket.connect` and
  `socket.create_connection` replaced by a raiser, and returned a normal answer,
  which is the operational meaning of "no implied collector";
- the four spans produced were `agent.invoke`, `planner.plan`, `tool.execute`
  (`tool.name=get_device_status`, `status=not_found`) and `synthesize`
  (`evidence.count=1`). No `rag.retrieve` and no `llm.request` span was invented
  for a step that did not run;
- a span opened with `query`, `device_id` and `request_id` attributes recorded
  none of them, while the allowed `status` attribute survived.

**RAG.** With the external checkout bind-mounted read-only, the retrieval metrics
read `industrial_agent_rag_requests_total{provider="local",status="success"} 1`

outcomes stayed distinct. A write attempt inside the container returned
`Read-only file system`, and `git status --porcelain` in the external checkout
reported **0** changed files before and after.

`uci_metropt3`, and the dataset was absent from the image (`0` CSV files under

### Measured overhead

| Component | Planning mean | Total mean |

| Metric recording | -0.0001 ms | +0.0112 ms |
| Span creation | +0.0497 ms | +0.1506 ms |
| Per-stage logging | +0.0949 ms | +0.1834 ms |

Metric recording is below the noise floor of the host: the `off` configuration
alone varies by 0.031 ms between runs. The largest cost is the logging, which is

reporting a small number, and the report states which comparisons are measured
and which are derived from published figures.

## Known limits

- The overhead figures come from one host and one process layout. They are not
  container measurements; the container validation checks that metrics are
  produced, not how long they take.
- The absolute planning figure in the overhead report is larger than the 0.2103
  ms in `evaluation/reports/rule_baseline.json`, and the difference is explained
  there. The residual 0.0375 ms is not attributed and is not claimed as
  observability cost.
- No dashboard, alert rule or log shipper ships with the repository. The metrics
  are produced; what to alert on is a deployment decision.
- No tracing backend is assumed. Spans stay in the process unless an endpoint is
  named, and no collector is contacted by default.
- `provider="unknown"` on a retrieval that could not be built reports that no
  provider exists rather than which provider was configured. The reason is in the
  log event, not in the label.
- A cold process exposes the metric declarations but no series until something is
  observed, so a dashboard rule must tolerate an absent sample.

## Upgrading

Nothing is required. The defaults are `LOG_FORMAT=text`, `METRICS_ENABLED=true`
and `OTEL_ENABLED=false`, so an existing deployment keeps its log format, gains a
working `/metrics` endpoint, and imports nothing it did not import before. To
trace, install `requirements-otel.txt` or build with `INSTALL_OTEL_DEPS=1` and set
`OTEL_ENABLED=true`.

No tool changed its name or its schema. No planner behaviour changed. No benchmark
number changed.
