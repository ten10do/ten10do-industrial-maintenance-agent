# Industrial Maintenance Agent v0.8.4

Docker RAG runtime readiness.

## The problem

The published image installed `requirements.txt` only. The local RAG provider
imports the Industrial Knowledge RAG retrieval engine in-process, and that
import needs the packages listed separately in `requirements-rag-local.txt`
(`pypdf`, `numpy`, `scikit-learn`).

As a result the Docker path documented in the README did not work. Mounting a
RAG checkout and setting `RAG_PROVIDER=local`, `RAG_REPO_ROOT`, `RAG_BACKEND`
and `RAG_RETRIEVAL_MODE` was necessary but not sufficient. The container still
started, reported itself healthy, and answered a manual query with the manual
tool reported as unavailable, because the in-process import failed.

That failure mode is the reason this release exists. A missing optional
dependency looked identical to a working container from the outside.

## Added

- A second build shape from the same Dockerfile, selected by the
  `INSTALL_RAG_DEPS` build argument. It defaults to `0`, so the standalone image
  is unchanged and still carries no optional RAG dependency.
- A reproducible RAG build path. `requirements-rag-local.txt` is copied into the
  build context and installed only when `INSTALL_RAG_DEPS=1`.
- A Compose profile named `rag` with a second service, `agent-rag`. It builds
  with `INSTALL_RAG_DEPS=1`, sets the four RAG variables, and bind-mounts an
  external RAG checkout read-only at `/rag` through
  `${RAG_HOST_REPO:-../industrial-knowledge-rag}:/rag:ro`. No host path is
  hardcoded in the tracked files.
- Regression tests in `tests/test_docker_config.py`. They assert the opt-in
  default, the guard on the optional install, the profile placement, the
  read-only mount and the absence of a committed absolute host path. Docker
  itself is not invoked, so the hermetic CI job can run them.
- README Docker documentation split into a standalone section and a
  RAG-enabled section, with the full sequence from clone to query.

## Validation

Both shapes were built and run against a real Docker daemon, not inspected
statically.

Standalone image, `INSTALL_RAG_DEPS=0`:

- Build succeeded, container reached `healthy`, `GET /health` returned 200, and
  `GET /` reported `version: 0.8.4`.
- A `PLC-001` device query returned HTTP 200 with `planner_used=rule`,
  `internal_error` absent, and real device detail in the answer.
- Runs as `uid=10001(app)`, not root. Python 3.11.16. `/app/data` writable,
  `/` not writable.
- `pypdf`, `numpy` and `sklearn` are absent from this image. That is the
  intended state.
- After `docker restart`, the container returned to healthy and the named volume
  preserved the seeded device rows.

RAG-enabled image, `INSTALL_RAG_DEPS=1`, started through the Compose profile:

- Build succeeded and the container reached `healthy`.
- `pypdf` 6.18.1, `numpy` 2.4.6 and `scikit-learn` 1.9.1 all import inside the
  container.
- A manual query returned HTTP 200 in 2228.07 ms with
  `tools_called=["search_maintenance_manual"]`, `internal_error` absent, and
  `tool_status` reporting `found=true`.
- Four document evidence items were returned, from `PowerFlex_527_User_Manual.pdf`
  page 112 and `PowerFlex_520_User_Manual.pdf` pages 161, 84 and 7, with
  `provider: local` and retrieval mode `hybrid`.
- The only copy of the RAG retrieval module inside the container resolves to the
  mounted checkout. The external repository is not baked into the image.
- Docker reports the mount as `rw=false`. A write attempt from inside the
  container was rejected with `Read-only file system` and left no residue. The
  external repository's working tree stayed clean.

Image size, measured on the validation host:

| Image | On disk | Compressed |
| ----- | ------- | ---------- |
| `industrial-maintenance-agent:0.8.4` | 383 MB | 83,609,823 bytes |
| `industrial-maintenance-agent:0.8.4-rag` | 759 MB | 167,865,525 bytes |

The optional dependency set roughly doubles the image, which is why it stays out
of the default build.

Neither image contains a `.env` file, a credential-shaped environment variable
or a host-specific path. The only credential-shaped variable in either image is
`GPG_KEY`, inherited from the `python:3.11-slim` base image.

## Compatibility

No API-breaking changes.

No planner logic, prompt, tool schema, evaluation dataset, benchmark report or
benchmark metric changed. The frozen 49-case dataset is byte-identical to
v0.8.3.
